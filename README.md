Подход
Как нашли "сиды" (первичный список компаний)
Первичный список (~105 компаний) был сформирован из открытых отраслевых рейтингов с ключевым улучшением: для каждой компании заранее собраны данные о масштабе клиентской базы (clients_millions) и источнике этой информации (client_source). Это позволило сразу применять самое надёжное правило Уровня B.

Как определяли признаки поддержки (каналы/раздел/FAQ/24/7)
Парсинг сайтов + анализ структурированных данных. Помимо стандартного парсинга HTML с regex-паттернами, в алгоритм была заложена приоритетная проверка поля clients_millions из seed-данных.

Как доказывали "10+"
Иерархия A > B с ключевым усовершенствованием:

Уровень A (прямое доказательство с сайта/новостей): "колл-центр на 200 операторов" → support_team_size_min = 200.

Уровень B (нижняя оценка) - ПРИОРИТЕТНОЕ ПРАВИЛО:

Если в seed есть clients_millions (как у "СберПрайм": 20 млн), применяется отраслевая формула:

text
support_team_size_min = max(10, clients_millions * 1_000_000 / INDUSTRY_RATIO[category])
*Пример для банка (ratio=2000): 20,000,000 / 2000 = 10,000 → ограничено 1000.*
Это самое сильное доказательство Уровня B, так как опирается на объективные публичные данные.

Дополнительные правила (если clients_millions нет):

24/7 + смены → min 12 чел.

3+ вакансии поддержки → вакансии × 2.

Как мёржили компании
Агрегация по inn как уникальному ключу. При конфликте данных приоритет: Уровень A > Уровень B (clients_millions) > остальные правила B.
Что получилось / что не получилось
Что удалось (сильные стороны):

Использование структурированных данных о клиентской базе — главное конкурентное преимущество подхода. Это даёт наиболее обоснованные оценки для Уровня B.

Рабочий пайплайн с понятной иерархией доказательств.

Реализация отраслевых коэффициентов для реалистичных расчётов.

Что не успели / ограничения (сыроватость):

"Бутстрап-ограничения": В реальном продакшене задача решается подключением платных API (DaData, Contour.Focus) для мгновенного получения ИНН, выручки, численности сотрудников и проверки активности компаний. В рамках тестового задания использовались только бесплатные и общедоступные источники, что накладывает естественные ограничения на скорость и полноту данных.

Синхронная архитектура: Текущая реализация использует последовательные HTTP-запросы с паузами между ними. Переход на асинхронный подход (asyncio/aiohttp) позволил бы ускорить парсинг в 5-10 раз при том же количестве компаний, что критически важно для масштабирования.

Оптимизация скорости: Парсинг 100+ сайтов с уважительными паузами занимает 45-60 минут. Для продакшена необходимо кэширование, parallel-обработка и, возможно, использование headless-браузеров для обхода блокировок.

Обработка динамического контента: Текущий парсер не работает с JavaScript-сайтами (SPA), что является ограничением для современных веб-ресурсов.

Валидация доказательств: Не реализована перекрёстная проверка цифр из разных источников.

Роль LLM
Не использовалась. Все решения закодированы rule-based, что обеспечивает полную прозрачность и воспроизводимость, но требует ручной настройки правил.
